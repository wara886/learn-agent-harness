# Learn Agent Harness 产品定义与交付 SOP

> 状态：需求候选稿，未冻结
> 范围：从 0 到 1 的学习产品定义、课程生产和交付流程
> 事实基线：`onychen/learn-dsh@249f4a0`；`deepseek-harness@47f943859b`
> 核心反馈：用户认为现有产品“感觉太工程了，都看不进去”。这不是文案润色问题，而是产品入口、学习顺序和信息披露方式的问题。

## 1. 产品结论

Learn Agent Harness 应该先让学习者看到一个 Agent 如何完成具体任务，再帮助他解释刚才发生了什么，最后才展开 Pi、Cordis、事件模式、包结构和真实源码。

产品的第一承诺不是“讲完 DSH 的全部架构”，而是：

> 从一次看得见的 Agent 行动出发，逐层看懂它为什么能调用工具、记住过程、扩展能力、委派任务并被追踪。

课程目录不是首页主体。架构图、22 课全量清单、代码行数、包映射和实现免责声明都属于按需展开的信息。主路径始终采用“任务与结果 -> 观察变化 -> 形成直觉 -> 给概念命名 -> 查看最小实现 -> 对照真实 DSH”的顺序。

## 2. 问题定义

### 2.1 核心问题

现有 `learn-dsh` 把工程结构当作学习结构。内容对已经理解 Agent runtime、事件系统和依赖注入的工程师有参考价值，但要求新学习者在获得第一个实际结果之前，先接受完整课程规模和大量陌生术语。

用户说“太工程了，看不进去”意味着当前产品未完成三个基础任务：

1. 没有先回答“学完能做什么”。
2. 没有让用户在低成本操作中先获得可见结果。
3. 没有根据学习者当前理解程度隐藏暂时不需要的工程细节。

### 2.2 现有产品审计

| 维度 | 当前表现 | 学习阻力 | 产品要求 |
|---|---|---|---|
| 受众 | 同时面向框架维护者、Agent 开发者和初学者，未明确主次 | 初学者无法判断前置知识，维护者也难以快速查找 | 主受众固定为“会基础编程、用过 Agent，但不了解 DSH 内部机制的应用开发者” |
| 信息架构 | 首页同时展示 7 个阶段、22 课和 1 个附录 | 在开始前先暴露全部学习成本 | 首页只呈现一个起点、三类常见任务和可继续的最近进度；完整目录进入二级入口 |
| 课程顺序 | 先 Agent Loop，再 Cordis、事件、日志等架构分层 | 第二课即进入框架内部机制，任务动机尚未建立 | 先完成任务，再因任务遇到的问题引出日志、插件、作用域和 Provider |
| 首屏 | “学习路径”标题、架构 tagline、搜索、7 阶段图例、长侧栏 | 首屏解释课程组织，而不是展示学习收益；移动端正文排在完整侧栏之后 | 首屏显示一个真实任务、一段可运行体验、一个主操作和预期用时 |
| 术语密度 | 首屏和前几课密集出现 Cordis、waterfall、shadowing、seam、SessionEvent、projection | 学习者要同时记忆名词、关系和实现 | 每课核心路径最多引入 3 个新术语；先用普通语言解释现象，再给术语命名 |
| 课程节奏 | 每课固定八段，含运行、架构图、代码拆解、真实包映射 | 结构稳定但每课都要求从运行跳到工程解释；缺少预测和动手改变 | 每课围绕一个问题、一个可见状态变化和一个机制，核心路径可独立完成 |
| 交互反馈 | 主要是阅读讲义或整段源码 | 用户看见信息，但没有形成“操作 -> 反馈 -> 解释”的闭环 | 每课至少包含一次预测、一次操作和一次结果对比 |
| 内容定位 | Python 玩具实现与 TypeScript 真实实现并列 | 学习者容易把教学模型误认为真实 API，或认为必须学两套实现 | 教学模型明确标记为“概念演示”；真实 DSH 对照独立折叠，并标注版本和证据 |

### 2.3 需要保留的现有价值

新产品不照搬现有页面，但保留以下有效资产：

- 单课可以离线运行并得到确定输出。
- 从小机制逐步走向完整 Agent 的教学意图。
- 每课说明教学简化和真实 DSH 的差异。
- 可查看讲义与源码。
- Session、工具、插件、作用域、上下文、委派和组装等主题覆盖较完整。

## 3. 目标用户与学习情境

### 3.1 主用户

主用户是会读基础 JavaScript、TypeScript 或 Python，使用过聊天式 Agent 或编码 Agent，但没有维护过 Agent runtime 的应用开发者。

他通常在以下情境进入产品：

- 想判断 DSH 是否适合自己的 Agent 项目。
- 遇到工具调用、上下文、子 Agent 或可观测性问题，想理解 DSH 如何处理。
- 准备修改或扩展 DSH，但直接读 monorepo 不知道从哪里开始。
- 看过架构文档，仍无法把名词与一次真实运行对应起来。

### 3.2 次用户

- 需要快速定位真实包和扩展点的 DSH 贡献者。
- 需要用一条可演示路径向团队解释 DSH 的技术负责人。
- 想比较不同 Agent harness 设计的框架作者。

次用户通过“完整地图”“真实源码”和“机制索引”进入，不改变主路径的难度。

### 3.3 不作为主用户的人群

- 从未写过代码、只想使用成品 Agent 的终端用户。
- 只需要 API 字段定义和配置表的维护者。
- 只想复制一套生产部署模板的运维人员。

产品可以给这些人明确去向，但不为同时覆盖所有人而增加主路径内容。

## 4. Jobs To Be Done

### 4.1 主要 JTBD

当我第一次接触 DSH 时，我想通过一个能立即看到结果的 Agent 任务，理解请求、模型、工具和结果之间发生了什么，以便判断是否值得继续学习。

当我准备修改 DSH 时，我想从用户可见行为反查负责它的机制、事件和包，以便知道应该扩展哪里，而不是从 monorepo 猜入口。

当 Agent 出现忘记上下文、重复执行、子任务失控或过程不可见时，我想用一条实际轨迹理解 DSH 的处理方式，以便形成可用于排障的心智模型。

### 4.2 次要 JTBD

- 我想只学习与当前问题有关的模块，而不是先完成 22 课。
- 我想确认教学解释对应哪个 DSH 版本和哪段权威实现。
- 我想在手机或短暂空闲时间理解概念，回到电脑后继续运行和读源码。
- 我想保留学习进度，并从上次尚未理解的检查点继续。

## 5. 非目标

- 不替代 DSH 的 API 参考、配置参考和维护者架构文档。
- 不按 monorepo 包目录逐一讲解所有实现。
- 不承诺一次学完 DSH，也不把“完成 22 课”当作唯一成功。
- 不把 Python 教学实现包装成生产 SDK 或真实 DSH API。
- 不在主路径解释所有 Cordis 机制、事件类型和生命周期例外。
- 不以炫技式动效、积分或连续签到掩盖内容理解问题。
- 不复制参考站点的信息架构和视觉样式后只做表面优化。
- 不在没有权威源码证据时补写“合理但未验证”的 DSH 行为。

## 6. 产品原则

1. **结果先于目录。** 用户先看到 Agent 完成任务，之后再知道该结果属于哪一课。
2. **问题先于机制。** 先出现“为什么它忘了”“为什么工具能被替换”，再引入 SessionEvent 或 Provider。
3. **普通语言先于术语。** 术语用于压缩已理解的概念，不用于制造专业感。
4. **一次只增加一个认知变量。** 每课只回答一个问题、改变一个关键状态、解释一个核心机制。
5. **先预测，再观察。** 学习者在运行前做一个选择或预测，运行后比较结果。
6. **实现按需展开。** 核心路径不依赖阅读长源码；最小实现和真实 DSH 分为两个深度层。
7. **教学模型与产品事实分开。** 类比负责建立直觉，权威源码负责陈述事实，两者必须显式标记。
8. **任意一课都能找到入口和出口。** 用户可从问题搜索进入，完成后知道已学会什么、下一步为何相关。
9. **移动端先看到正文。** 导航不得把正文推到首屏之后。
10. **进度代表能力，不代表翻页。** 完成条件是操作或检查点通过，不是滚动到页底。

## 7. 用户旅程

### 7.1 首次访问

1. 用户在首屏看到具体任务，例如“看一个 Agent 如何查文件并给出答案”。
2. 用户知道无需先理解架构，也知道完成首次体验所需的大致时间和前置条件。
3. 用户点击唯一主操作，看到请求进入、工具被选择、结果返回和 Agent 停止。
4. 产品只标出两个值得观察的变化，不立即解释所有事件。
5. 用户回答一个预测或判断题，获得即时解释。
6. 用户选择继续理解该机制、切换到自己的问题，或查看完整学习地图。

### 7.2 主线学习

1. 每个单元从一个用户可见问题开始。
2. 用户操作演示或运行固定示例。
3. 产品对比操作前后状态，并用普通语言解释。
4. 产品给刚才的机制命名，展示一张局部关系图。
5. 用户只修改一个参数、事件或插件，验证理解。
6. 需要工程细节的用户展开最小代码和真实 DSH 对照。
7. 用户完成迁移题或口述检查点，产品记录能力进度。

### 7.3 从问题进入

搜索和问题入口使用用户语言，例如“上下文太长”“子 Agent 一直开新任务”“工具为什么没执行”。结果先返回相关任务课，再提供术语和源码结果。搜索不得只匹配课程标题和 motto。

### 7.4 回访

首页首先显示“继续上次任务”和已掌握的能力，不要求用户重新寻找课号。用户可以切换到完整地图、术语索引或真实源码索引。

## 8. 渐进披露课程结构

### 8.1 四层阅读深度

每个主题都采用相同的四层深度，但默认只展示前两层：

| 层级 | 用户问题 | 默认状态 | 内容 |
|---|---|---|---|
| 体验层 | 它做了什么？ | 展开 | 可运行任务、可见输入输出、一次操作 |
| 理解层 | 为什么会这样？ | 展开 | 状态变化、局部图、普通语言解释、术语命名 |
| 实现层 | 最小机制怎么写？ | 折叠 | 仅包含本课变化的代码、关键事件、失败路径 |
| DSH 对照层 | 真实项目在哪里实现？ | 折叠 | 固定版本、Service Definition / Provider / Consumer、源码位置和教学差异 |

用户可以直接进入任意层，但页面不得用实现层的信息压住体验层。

### 8.2 课程主线

完整内容组织为一段首次体验和六个任务章节。章节名表达用户目标，工程术语只作为副标题或索引标签。

#### 0. 第一次让 Agent 完成任务

- 给 Agent 一个查找并回答的问题。
- 观察模型选择工具、接收结果并停止。
- 建立“请求 -> 决策 -> 行动 -> 结果”的最小循环。

对应机制：Agent loop、工具调用。Cordis 和事件系统不在首次体验中展开。

#### 1. 让它记住刚才发生了什么

- 任务：连续提问后回看 Agent 的依据。
- 问题：聊天消息从哪里来，为什么过程能够重放？
- 对应机制：SessionEvent、消息投影、Turn / Step、显式 Trace。

#### 2. 加能力，但不改 Agent 主干

- 任务：加入一个工具或拦截规则，再撤销它。
- 问题：能力如何注册、组合和回退？
- 对应机制：Cordis 插件、effect、类型化事件、工具注册与执行管线。

#### 3. 给不同 Agent 不同能力

- 任务：让两个 Agent 使用不同的工具、提示和模型。
- 问题：同名能力如何选择，模型和实现如何替换？
- 对应机制：Scope、shadowing、LLM Provider、System Prompt、Service Definition / Provider / Consumer。

#### 4. 上下文快满时继续工作

- 任务：在长对话中按需加载知识并压缩旧过程。
- 问题：什么必须保留，什么可以从模型当前视图移出？
- 对应机制：Skills、Compaction、append / replace 语义。

#### 5. 把大任务交给别的执行单元

- 任务：拆分一个长任务，同时控制并发、成本和回传内容。
- 问题：子任务如何隔离、后台工作如何回到主流程、目标如何继续？
- 对应机制：Subagent、Jobs、Goal、Goal Round Driver。

#### 6. 组装、追踪并解释一个完整产品

- 任务：组合一个 mini DSH，替换一项能力并追踪完整执行。
- 问题：部署组合如何形成，出错时如何回到事实记录？
- 对应机制：Profile、Bundle、Capstone、Trace、持久化附录。

### 8.3 辅助入口

- **按问题找课：** 使用用户问题和故障现象组织。
- **完整架构地图：** 面向已有心智模型的学习者，展示全部课程和依赖。
- **术语索引：** 每个术语包含普通语言解释、首次出现课和权威位置。
- **真实源码索引：** 按用户行为映射到包、服务、事件和文档。
- **教学实现索引：** 明确它是概念演示，不与真实 API 混排。

## 9. 每课标准模板

每课必须满足“一问、一变、一机制”。标准模板如下：

1. **这次要完成什么**
   用用户任务命名，列出预期结果、预计时间和必要前置知识。不得用包名或内部类型作为主标题。

2. **先猜一下**
   提供一个可验证的选择或预测。问题必须与随后可见状态变化直接相关。

3. **动手运行**
   提供一个主操作。默认路径应在 90 秒内出现第一个可见结果，不要求先读长说明。

4. **看哪里变了**
   只标注 2 至 3 个关键变化，使用输入前后、事件前后或能力有无的对比。

5. **现在给它一个名字**
   先用普通语言完整解释，再引入最多 3 个新术语；每个术语都链接到术语索引。

6. **只改一个地方**
   用户改变一个参数、插件、事件或状态，预测并验证新的结果。该操作是课程完成条件。

7. **最小实现，可选**
   只显示本课新增或改变的代码。核心代码块建议不超过 25 行；更长内容通过差异视图或源码链接提供。

8. **真实 DSH 对照，可选**
   标明权威提交、真实角色名称、事件模式、包与源码位置，并列出教学模型省略的行为。

9. **带走什么**
   用一个新场景检查迁移能力，而不是重复术语定义；给出下一课与当前问题的因果关系。

### 9.1 内容预算

- 首屏只允许一个主操作，不显示完整课程表。
- 核心路径每课建议 5 至 12 分钟；超过 12 分钟时优先拆课或把工程细节移入可选层。
- 每课最多引入 3 个新术语，术语首次出现时必须有普通语言解释。
- 核心路径只保留理解当前状态变化所需的代码。
- 每个段落只承担一个教学目的；同一事实只有一个详细解释位置。
- 比喻只能帮助建立第一层直觉，随后必须给出其失效范围。

这些预算是首版设计约束，不是既有用户数据。试点结果可以触发正式变更。

### 10.1 P0：没有这些能力不得进入试点

| 需求 | 验收行为 |
|---|---|

### 10.2 P1：P0 试点稳定后排期

- 根据目标、问题和经验推荐不同学习路线。
- 教学代码与真实实现的结构化差异视图。
- 可分享的学习检查点和局部运行轨迹。
- 术语关系图与跨课复习。
- 无需登录的匿名学习数据导出和清除。

### 10.3 P2：有证据再决定

- 登录和跨设备同步。
- 社区作业、排行榜或成就体系。
- 浏览器中的完整开发环境。
- AI 导师自动解释和个性化课程生成。

## 11. 内容事实校验流程

### 11.1 权威顺序

DSH 事实按以下顺序判断：

1. 固定提交中的公开类型、服务定义和运行代码。
2. 同一提交中的测试与可运行示例。
3. 同一提交中的架构文档、包 README 和已实施 Agent Note。
4. 参考课程及其教学代码。
5. 作者类比和推断。

下级材料不得覆盖上级材料。参考课程是待审计输入，不是事实来源。

### 11.2 声明分类

| 类别 | 示例 | 发布要求 |
|---|---|---|
| 产品事实 | 某事件采用 waterfall，某字段为字符串联合 | 必须链接固定提交中的代码或测试；能自动检查时加入断言 |
| 教学模型 | 用简化日志演示消息投影 | 标记“概念演示”，列出与真实实现的差异 |
| 类比 | 把 append-only log 比作账本 | 标明类比失效范围，不作为 API 行为依据 |
| 推断 | 某设计可能降低耦合 | 明确写为解释或推断，不伪装成已承诺行为 |

### 11.3 单课事实校验步骤

1. 内容作者先列出本课所有可验证声明，不从正文中临时挑选。
2. 为每项声明记录 DSH 提交、文件、符号或测试，以及用户可见结论。
3. 事实审核人直接读取权威材料，判定为“准确”“需限定”“错误”或“当前无证据”。
4. 内容作者先修改事实表，再修改教学文案和演示。
5. 对事件模式、联合类型、配置键、包名和源码路径建立自动断言或链接检查。
6. 教学演示运行基线、成功路径和至少一个与本课结论相关的失败路径。
7. 第二位审核人确认普通语言解释没有改变原事实的条件、时机或例外。
8. 发布物显示“适用于 DSH `<commit>`”，并提供勘误入口。

### 11.4 上游漂移处理

- 更新权威提交前先生成声明差异报告，不直接批量替换版本号。
- 任何失效的事实断言都会阻止发布。
- 源码位置变化但行为未变时更新证据；行为变化时重新审查课程任务、解释和检查点。
- 无法确认的内容降级为待验证，不以模糊措辞保留在主路径。

## 12. 需求冻结门

开发首个纵向切片前，以下材料必须同时达到“已确认”：

- 主用户、次用户、JTBD 和非目标。
- 首次访问、主线学习、问题进入和回访旅程。
- 六章信息架构与三节纵向切片的具体课题。
- 每课模板、内容预算和术语表。
- 事实声明表及权威提交。
- 桌面与 390 px 移动端的低保真流程。
- P0 验收场景、无障碍要求和测量事件字典。
- 参考项目的可复用资产清单与明确不沿用项。
- 隐私、许可证和署名方案。
- 负责人、评审人、发布日期候选和回退负责人。

### 12.1 冻结评审

冻结评审至少包含 PM、学习内容负责人、DSH 事实审核人、设计负责人和开发负责人。每个角色必须给出明确结论：通过、带条件通过或不通过。未关闭的 P0 分歧视为不通过。

### 12.2 冻结后的变更

冻结后新增需求必须记录：解决的用户问题、证据、影响范围、被替换的优先级、事实与课程影响、交付日期影响和回退方式。没有被替换项的新增 P0 需求默认进入下一阶段，不插入当前纵向切片。

## 13. 从设计到发布的 SOP

### 阶段 A：证据与需求确认

**输入：** 用户反馈、参考课程、历史会话、权威 DSH 提交。
**动作：** 访谈或回放代表性学习过程；记录进入原因、首个卡点、放弃点和期望任务；完成现有内容与事实审计。
**产物：** 问题陈述、用户分层、JTBD、事实问题清单、竞品可复用项。
**退出条件：** 团队能用同一句话描述主用户、第一次成功和不服务的人群。

### 阶段 B：课程与交互原型

**输入：** 已确认的问题和 JTBD。
**动作：** 只设计三节纵向切片：首次任务、一次记忆/追踪任务、一次插件扩展任务；先写输入输出和状态变化，再写解释；制作桌面与移动端原型。
**产物：** 可点击流程、三课内容样稿、术语表、事实声明表。
**退出条件：** 至少 5 名主用户完成原型测试；至少 4 人无需主持人解释即可找到主操作并说出每课的核心状态变化。未达到时继续改原型，不扩写全课程。

### 阶段 C：需求冻结

**输入：** 原型测试记录和修订后的 P0。
**动作：** 按第 12 节完成跨角色评审，关闭所有 P0 分歧。
**产物：** 冻结版本、验收场景、排期、负责人。
**退出条件：** 所有必需角色明确通过；每项 P0 都有可观察的验收行为。

### 阶段 D：纵向切片开发

**输入：** 冻结需求和三课样稿。
**动作：** 先打通首页到三课完成、进度恢复、搜索、真实源码对照和事实校验；同步完成移动端、键盘和读屏路径；埋点只记录指标所需事件。
**产物：** 可部署纵向切片、测试记录、事实校验报告。
**退出条件：** 三课主路径在目标视口和输入方式下通过；事实检查无未解决错误；没有 P0/P1 无障碍问题。

### 阶段 E：课程扩展

**输入：** 纵向切片真实使用数据和访谈结论。
**动作：** 逐章扩展，每次只生产一个完整章节；沿用已验证模板；新增事实先进入声明表；每章发布前做迁移题测试。
**产物：** 六章主线、问题索引、术语索引、真实源码索引。
**退出条件：** 每章均满足内容、事实、交互和可访问性验收，不因赶齐课数而降低门槛。

### 阶段 F：发布与维护

**输入：** 全部 P0 验收证据。
**动作：** 发布版本和适用的 DSH 提交；监控首个结果耗时、课内放弃、运行失败、搜索无结果和事实漂移；定期处理勘误。
**产物：** 发布记录、指标看板、勘误记录、上游版本更新决策。
**退出条件：** 发布后维护负责人、事实更新周期和回退版本均已明确。

## 14. 设计 SOP

1. 先画用户操作和可见状态，不从页面组件或课程目录开始。
2. 每个页面标出唯一主任务、必要辅助任务和可删除信息。
3. 首屏测试顺序为：我能做什么、从哪里开始、多久看到结果、是否需要安装。
4. 桌面与移动端同步设计；390 px 视口不得把正文排在完整目录之后。
5. 导航、搜索、标签、代码展开和进度控件采用语义元素，并定义键盘与读屏状态。
6. 动效只用于说明状态变化，并提供 reduced motion 行为。
7. 在高保真设计前，用三节纵向切片完成主用户可用性测试。
8. 设计评审必须展示加载、空结果、运行失败、事实版本失效和进度恢复状态。

## 15. 内容 SOP

1. 从用户任务和预期输出写起，不从机制定义写起。
2. 写出“操作前状态”和“操作后状态”，确认只有一个核心变化。
3. 写预测题和单变量修改，再写解释。
4. 用普通语言解释完整行为，随后引入术语和局部关系图。
5. 把代码分成核心变化、可选最小实现和真实 DSH 三层。
6. 建立事实声明表，完成第 11 节校验。
7. 用新场景编写迁移检查点，避免只考术语记忆。
8. 由不了解本课实现的编辑做可读性检查，再由事实审核人做准确性检查。
9. 运行教学示例并保存预期结果；修复失败后重新执行，不手工修改结果文本。
10. 发布后将用户误解按“入口、解释、交互、事实”分类，回到对应内容层修正。

### 15.1 分段写作与独立 Agent 审核

课程扩展采用“先冻结大纲，再一次写完一个学习闭环，最后独立审核”的方式。“部分”按一课或一个可独立验收的学习闭环划分，不按段落、按钮或小标题划分；否则每次 Agent 的固定提示词和工具 schema 成本会高于局部文案本身。

1. 根负责人先冻结每部分的 `sectionId`、用户问题、可见结果、状态序列、单变量实验、完成检查、新术语、`claimId`、教学简化、篇幅和风险等级。
2. 作者只接收本部分大纲、相关 claim cards、前后部分短摘要、允许修改范围和验收命令，不读取完整会话、全部研究报告或整个仓库。
3. A 级新课或状态机由一名作者完成后，分别交给一名事实审核 Agent 和一名学习体验审核 Agent；B 级学习路径变化只做体验审核，C 级事实变化只做事实审核，D 级机械修改不用 Agent。
4. 事实审核只验证新增或变化的产品事实、固定提交证据和教学简化；已通过且基线、内容哈希和使用语义未变的 claim 直接复用。
5. 学习体验审核只检查入口、认知顺序、默认阅读负担、状态说明和完成条件，不重新扫描 DSH 或改写事实结论。
6. 审核只返回 `PASS`、`REVISE` 或 `BLOCK` 及最多 5 个可定位问题；根负责人裁决一次，不让审核 Agent 对话，也不启动第三个 Agent 投票。
7. 每部分最多一次定点修订和一次差异复查；仍为 `BLOCK` 时缩小范围、撤回 claim 或延期，不自动增加 Agent。
8. 全局同时运行的子 Agent 不超过 2 个，子 Agent 禁止再次委派；根负责人确认全部相关 Agent 已结束或取消后，才能宣布该部分完成。
9. 每部分记录输入、输出、缓存读取、固定注入、模型轮次和墙钟时间。任何一项达到预算就停止新工作，先交付已完成状态和未决项。
10. 打招呼、确认收到、状态查询、单句反馈、错字、格式、lint、schema 和链接检查使用当前回合或确定性脚本，不创建子 Agent。

完整预算、上下文包和结构化审阅格式见 `research/section-agent-review-workflow.md`。

## 16. 开发 SOP

1. 以三课纵向切片验证数据结构、路由、交互和内容生产流程，不先搭空的全站框架。
2. 课程内容、事实证据和 UI 状态使用结构化字段，避免从 Markdown 文案猜测完成条件或源码映射。
3. 搜索索引正文、用户问题、故障现象、术语和源码位置，并记录无结果查询。
4. 进度默认保存在本地，提供导出、清除和重新开始；登录不是 P0 依赖。
5. 页面状态更新后保留合理焦点，不用整页重建破坏输入和读屏上下文。
6. 所有可点击课程入口使用链接；图标按钮有可访问名称；自定义交互提供键盘等价操作。
7. 每项 DSH 产品事实带版本和证据标识，事实断言与链接检查进入持续集成。
8. GUI 变更使用真实构建验证桌面和移动端关键路径，并保留可复现的视觉证据。
9. 发布必须可回退到上一份课程数据和站点构建，不让内容更新与应用部署互相锁死。

## 17. 验收 SOP

### 17.1 产品与学习验收

- 新用户不查看完整目录即可开始首次任务。
- 首次任务在正常网络和目标设备上 90 秒内出现可见结果。
- 用户能指出操作前后的关键变化，并用自己的话解释本课机制。
- 用户能在新场景完成单变量修改或迁移题。
- 用户能找到与本课对应的真实 DSH 位置，但不需要阅读它才能完成核心路径。
- 返回用户能够继续最近任务或清除进度。

### 17.2 事实验收

- 所有产品事实均有固定提交证据。
- 所有教学简化均明确标记，并列出会影响理解的差异。
- 自动事实断言、教学示例、链接检查和内容构建全部通过。
- 事件模式、类型字段、角色名称、包名和源码位置与固定提交一致。

### 17.3 体验验收

- 390 x 844、768 x 1024、1440 x 900 三类视口完成关键路径且无信息遮挡。
- 键盘可以访问主导航、课程、搜索、折叠区、代码操作和前后课导航。
- 焦点可见，页面标题与标题层级有效，状态变化有读屏通知。
- reduced motion 下没有非必要位移动画。
- 搜索空结果、运行失败、内容缺失、版本失效和离线状态都有明确下一步。

### 17.4 发布门

出现以下任一情况不得发布：

- 存在已知事实错误或无证据的产品行为声明。
- 首次体验仍要求先阅读完整架构或安装说明。
- 移动端首屏看不到正文主任务。
- 关键路径存在 P0 或 P1 无障碍问题。
- 教学运行结果无法在干净环境复现。
- 没有可用的上一版本回退物。

## 18. 指标与测量方法

当前没有新产品基线。首个纵向切片负责建立基线，任何目标值都应在试点记录中标明样本、设备、入口和版本。

| 指标 | 定义 | 测量方法 | 用途 |
|---|---|---|---|
| 首个结果耗时 | 从首次进入到出现完整任务结果的时间 | 匿名记录首次页面事件与首次结果事件；用户测试用屏幕记录校验 | 判断入口是否仍然“太工程” |
| 首次体验启动率 | 看到首屏后启动任务的会话占比 | `first_view -> first_task_started` 漏斗 | 判断价值表达和主操作是否清晰 |
| 首课有效完成率 | 完成单变量修改或迁移检查点的会话占比 | 记录检查点结果，不以滚动或停留时长代替 | 判断是否真正形成理解 |
| 章节完成率 | 开始某章后通过章末迁移题的用户占比 | 按章节和入口分组 | 找出难度断层 |
| 课内放弃点 | 最后一次有效操作所在步骤 | 记录步骤事件，并结合访谈解释 | 区分内容、交互和运行问题 |
| 搜索无结果率 | 有效查询未返回结果的比例 | 记录去标识化查询分类和结果数 | 补充用户问题语言与索引 |
| 运行失败率 | 教学运行未得到预期状态的比例 | 按环境、课程、错误类型聚合 | 发现环境和示例可靠性问题 |
| 事实漂移数 | 升级 DSH 提交后失效的声明数量 | 事实断言和人工审计报告 | 控制课程与上游偏离 |
| 迁移成功率 | 用户面对未见过的相邻场景仍能选择正确机制 | 前后测使用不同题面，不提示术语 | 测量可迁移理解 |
| 自述理解度 | 用户能否用自己的话解释状态变化 | 访谈编码：完整、部分、错误、无法解释 | 补充行为指标，不作为唯一成功证据 |
| 回访继续率 | 回访后继续最近任务或主动选择下一任务的比例 | 匿名本地标识分组，提供退出统计 | 判断学习路径是否有持续价值 |

### 18.1 指标护栏

- 不用页面停留越长代表学习越好。
- 不用课数完成率替代迁移能力。
- 不为提高点击率增加虚假紧迫感或隐藏课程难度。
- 不收集完成上述指标不需要的源码、聊天内容或身份信息。
- 定量异常必须结合回放、访谈或错误记录解释后再改课程。

## 19. 风险与应对

| 风险 | 早期信号 | 应对 |
|---|---|---|
| 从“太工程”变成“太浅” | 贡献者找不到真实实现或关键例外 | 保留实现层和 DSH 对照层；主路径不承担参考文档职责 |
| 任务顺序扭曲真实架构 | 学习者会操作，但无法解释组件关系 | 每章结束回到局部架构图，最终提供完整地图和迁移题 |
| 教学模型被当成真实 API | 用户复制 Python 类名到 DSH | 显式标记概念演示，真实角色和源码使用独立视觉与版本标识 |
| 上游快速变化导致事实漂移 | 链接失效、事件或类型断言失败 | 固定提交、声明表、自动断言、版本升级审计 |
| 过度追求互动导致内容变慢 | 首个结果耗时上升，移动端卡顿 | 动效服务于状态解释；性能和 reduced motion 进入验收 |
| 一开始重写全部 22 课 | 大量内容完成后才发现模板无效 | 先交付三课纵向切片，通过用户测试再扩章 |
| 搜索仍按内部术语组织 | “上下文太长”等查询无结果 | 建立用户问题词表，审查无结果查询并映射到机制 |
| 进度机制制造压力 | 用户为了完成标记快速翻页 | 进度只在操作或检查点通过后更新，允许隐藏和重置 |
| 内容与前端互相等待 | 修改一课需要重新开发页面 | 课程、证据、交互状态结构化，建立独立内容预览和校验流程 |
| 参考仓库许可证或署名遗漏 | 发布前无法确认复用范围 | 在冻结门前完成资产清单、许可证审核和明确署名 |

## 20. 阶段退出与停止条件

### 20.1 继续扩展课程的条件

三课纵向切片只有同时满足以下条件，才扩展到完整六章：

- 至少 5 名主用户参与可用性测试。
- 至少 4 人无需主持人解释即可找到主操作并获得首次结果。
- 至少 4 人能指出关键状态变化，至少 3 人能完成未见过的相邻迁移题。
- 没有已知事实错误、P0/P1 无障碍问题或不可复现的教学结果。
- 用户反馈显示主要阻力已经从“看不进去/不知道从哪开始”转为具体课程问题。

这些是首轮产品门槛，不声称代表现有产品表现。

### 20.2 必须回到需求阶段的条件

- 用户普遍只把产品当参考索引，不愿完成任务式主线。
- 首次任务简化后仍无法让主用户理解产品收益。
- 三节课需要三套互不兼容的教学结构，标准模板无法成立。
- 为保持简单而不得不持续省略会改变结论的真实 DSH 行为。
- 主要需求实际来自无编程经验用户，当前主用户定义不成立。

### 20.3 暂停或终止当前方案的条件

- 权威 DSH 版本无法固定，产品事实无法稳定校验。
- 参考资产的许可证或署名要求无法满足计划中的复用方式。
- 团队没有明确的长期事实维护负责人。
- 试点显示任务式产品没有比轻量参考文档带来更好的理解或迁移能力，且两轮结构调整后仍无改善。

## 22. 首轮执行清单

1. 冻结主用户和三个优先问题：完成一次工具任务、回看一次过程、加入并撤销一项能力。
2. 为三个问题各写一课，不沿用原课程八段正文。
3. 建立参考课程声明审计表，优先处理事件模式、Session 表面操作、System Prompt、Skills 通知和 Service 角色术语。
4. 完成首次体验及三课的桌面和 390 px 移动端原型。
5. 招募至少 5 名主用户测试首个结果、状态变化理解和迁移题。
6. 根据测试修订产品定义，召开需求冻结评审。
7. 需求冻结后才进入纵向切片开发。
