# 分段内容生产与独立 Agent 审核流程建议

> 日期：2026-08-14
> 适用对象：`learn-deepseek-harness` 的课程、交互脚本和配套说明
> 结论：可行，但审核单位必须是一段完整学习闭环，而不是每个小标题；必须先冻结大纲，再按风险选择独立审核角色，并为整批工作设置固定 Token、Agent 和轮次上限。

## 1. 为什么可行，以及必须避免什么

“先分出大纲，一部分一部分写，每部分交给独立子 Agent 审核”适合这个项目。它能让不同课程共享同一学习顺序，又能阻止作者自行证明自己的内容正确。独立审核尤其适合检查 DSH 事实、术语引入顺序和“是否仍然太工程”这三类问题。

但不能把“部分”理解成每个段落、每个按钮文案或每个小标题。每次 Agent 回合都有固定上下文成本；用户截图中的简单对话已经出现约 `1.5K` 系统提示词和约 `6.4K` 工具说明。若每个小段都启动作者、事实审核和体验审核三个 Agent，仅固定注入就会重复约三次，审核成本可能高于正文。流程必须减少 Agent 启动次数，而不只是缩短正文提示词。

本流程把一个“部分”定义为可独立验收的内容单元，满足以下条件：

- 回答一个用户问题；
- 包含一次预测、一次操作、2 至 3 个可观察状态变化和一次检查；
- 有自己的完成条件和 `claimId` 集合；
- 删除该部分不会让相邻部分的句子或状态机失去语义。

在当前范围内，三课分别是三个部分。课内标题、过渡句、按钮文案和单个源码注释不另建 Agent 任务。

## 2. 总体流程

```text
根负责人冻结大纲
  -> 作者只写一个部分
  -> 按风险启动独立事实审核和/或学习体验审核
  -> 根负责人裁决结论
  -> 原作者只改被指出的问题
  -> 原审核人只复查差异
  -> 合并该部分，开始下一部分
```

作者和审核人不得递归创建子 Agent。所有 Agent 由根负责人直接创建、限制输入，并在同一部分完成或取消后结束。一个部分没有通过，不阻塞已经冻结且无依赖的其他部分起草，但不能提前宣布整批完成。

## 3. 大纲冻结门

大纲不是主题列表。每个部分只有具备以下字段才可进入写作：

| 字段 | 必须回答的问题 |
|---|---|
| `sectionId` | 如何稳定引用该部分？ |
| 用户问题 | 学习者此刻想解决什么？ |
| 可见结果 | 不读源码时能看到什么变化？ |
| 学习目标 | 完成后能用普通语言说明什么？ |
| 前置依赖 | 必须先学会哪一项？没有则写无。 |
| 状态序列 | 哪 2 至 3 个状态会依次变化？ |
| 单变量实验 | 只改变什么，预期结果是什么？ |
| 完成检查 | 哪个可机器判断或人工判断的行为算完成？ |
| 新术语 | 最多 3 个，何时才命名？ |
| `claimId` | 使用哪些既有事实声明，需要新增哪些？ |
| 教学简化 | 哪些真实行为被省略，是否会改变结论？ |
| 篇幅预算 | 默认层、展开层各允许多少内容？ |
| 风险等级 | 是否需要事实审核、体验审核或两者？ |

冻结条件：

1. 三课顺序、每课唯一问题和完成条件没有重叠。
2. 默认层先呈现任务与结果，工程术语、源码和包名进入可展开层。
3. 每项 DSH 事实已有 `claimId`，或明确标记为待建立的新 claim；不得以参考站原文代替证据。
4. 每部分都有独立边界，可单独写、审、撤回和发布。
5. 根负责人记录大纲版本，例如 `outline-v1`，并给出本批 Agent、Token、墙钟和并发预算。

冻结后可以调整句子、例子和单段交互。若要改变课程顺序、学习目标、完成条件、状态序列或 claim 结论，必须由根负责人列出受影响部分并生成新的大纲版本。作者或审核人不得在自己的任务中顺便扩展大纲。

## 4. 职责隔离

### 4.1 根负责人

- 冻结大纲、分配预算和提供最小上下文包；
- 决定一个部分需要哪些审核角色；
- 汇总结构化审核结果并裁决冲突；
- 检查所有 Agent 已结束或取消后，才宣布该部分完成；
- 维护 claim 注册表和跨部分术语表，不让各 Agent 重建全局事实。

根负责人不以“再让一个 Agent 总结所有 Agent”作为默认收尾。最终综合应直接从结构化审核结论和已合并内容生成。

### 4.2 部分作者

- 只实现指定 `sectionId` 的学习闭环；
- 使用已分配的 claim，不重新审计整个 DSH 仓库；
- 将普通语言解释、交互状态、工程展开层和教学简化分开；
- 在提交中列出实际新增或修改的 claim、术语和状态；
- 只根据根负责人确认的审核项修改一次，不与审核 Agent 争论。

作者不能审核自己的部分，也不能改动相邻部分来规避问题。

### 4.3 事实审核 Agent

- 只验证本部分新增或修改的事实声明；
- 对照 claim 注册表中的固定 DSH 提交、文件、符号、类型或测试；
- 检查教学简化是否会改变结论，以及“当前行为”“已知缺口”“建议设计”是否被混写；
- 给出可定位、可执行的阻塞项，不重写课程文风；
- 复用已有 PASS claim，不重复扫描同一证据。

涉及事件模式、类型字段、包名、角色名、生命周期或当前产品行为时必须启用事实审核。纯导航文案或已验证 claim 的机械复用不重复启动事实审核。

### 4.4 学习体验审核 Agent

- 以目标初学者视角检查任务入口、认知顺序、首次停顿点和默认阅读负担；
- 检查术语是否先于现象、一次是否要求多个决定、源码是否成为主路径前置条件；
- 检查状态和按钮文案能否说明“发生了什么、为什么停下、下一步做什么”；
- 依据既定学习目标审核，不凭个人视觉偏好扩写功能；
- 不重新判断 DSH 源码事实，发现疑问时引用 claim 交给事实审核。

新的学习路径、交互步骤、首页入口和完成检查必须启用体验审核。纯事实索引、自动生成的源码位置或机械格式修正不重复启动体验审核。

## 5. 风险分级与审核组合

| 风险 | 示例 | 作者 | 事实审核 | 体验审核 |
|---|---|---:|---:|---:|
| A：事实和学习路径均变化 | 新课、状态机、DSH 对照 | 1 | 1 | 1 |
| B：只改变学习路径 | 入口、步骤顺序、检查题 | 1 | 0 | 1 |
| C：只改变产品事实 | claim、源码证据、限定条件 | 1 | 1 | 0 |
| D：机械或低风险 | 错字、链接、格式、已审核 claim 的原样引用 | 根负责人或脚本 | 0 | 0 |

“每部分独立审核”落实为：每个 A、B、C 级可交付部分至少由一名没有参与写作的 Agent 审核。A 级部分使用事实和体验两个独立审核 Agent；B、C 级只启用相关角色。D 级工作不为满足形式而启动 Agent。

## 6. 最小上下文包

每个 Agent 只收到完成自身职责所需的材料。不得默认注入完整会话、整个仓库目录、全部研究报告或其他部分全文。

### 作者包

- 冻结大纲中该部分的单条记录；
- 全局产品原则摘要，最多 400 中文字；
- 前一部分结果和后一部分目标，各最多 150 中文字；
- 本部分 claim cards；
- 必需的数据 schema 或文件路径；
- 输出路径、允许修改范围和验收命令。

### 事实审核包

- 待审核部分的最终草稿或差异；
- 本部分引用和新增的 claim cards；
- 每个 claim 对应的最小源码片段、固定提交位置或测试输出；
- 七类已知参考错误的相关条目，而不是整份审计报告；
- 固定的结论格式。

### 学习体验审核包

- 待审核部分默认路径；
- 目标用户、学习目标和完成条件；
- 前后部分各一段摘要；
- R0-01 至 R0-05、R0-09 中与本部分相关的检查项；
- 如有界面，只提供关键视口截图和必要交互状态，不附整个代码仓库。

任何 Agent 认为上下文不足时，只能返回一个具体缺口，例如“缺少 `claim.tool-execute-mode` 的固定提交证据”。它不能自行遍历整个仓库补齐背景。根负责人决定补充材料、缩小问题或停止该任务。

## 7. 预算与并发

预算同时计算输入、输出、缓存读取、Agent 数、模型请求数和墙钟时间。缓存命中仍占用资源，不能因账单口径不同而从审计中消失。

### 单部分默认预算

| 环节 | Agent 数 | 输入上限 | 输出上限 | 模型轮次 | 墙钟上限 |
|---|---:|---:|---:|---:|---:|
| 作者初稿 | 1 | 5K Token | 2K Token | 1 | 15 分钟 |
| 事实审核 | 0 或 1 | 4K Token | 700 Token | 1 | 8 分钟 |
| 体验审核 | 0 或 1 | 3K Token | 700 Token | 1 | 8 分钟 |
| 定点修订 | 原作者 | 3K Token | 1.5K Token | 1 | 10 分钟 |
| 差异复查 | 原审核人 | 2K Token | 400 Token | 1 | 5 分钟 |

这些数值是可见任务上下文预算，另需在整批预算中预留运行环境固定注入。A 级部分最多使用 3 个独立 Agent 身份和 5 个模型轮次；B、C 级最多 2 个身份和 4 个轮次。每部分只允许一次修订和一次差异复查。仍然 BLOCK 时，由根负责人缩小部分、撤回 claim 或延期，不再自动创建新审核 Agent。

并发规则：

- 整批内容工作最多同时运行 2 个子 Agent；
- 同一部分的作者完成前不启动审核；
- A 级部分的事实审核和体验审核可并行，但并发总数仍为 2；
- 不同部分可以并行起草，但不得同时修改同一文件或同一 claim；
- 禁止子 Agent 再委派；禁止审核人互相发消息形成辩论链；
- 根负责人保留至少一个执行槽用于取消、验证和汇总；
- 达到任一预算上限即停止新工作，先输出已完成状态与未决项。

## 8. Claim 复用机制

维护唯一 claim 注册表。每条 claim 至少包含：

```yaml
claimId: claim.tools-execute.waterfall
statement: tools/execute 使用 waterfall 监听语义。
classification: current-behavior
baseline: deepseek-harness@47f943859b
evidence:
  - path: packages/...
    symbol: ...
caveat: 批量执行工具是否并发是另一项语义。
reviewStatus: pass
reviewedAt: 2026-08-14
contentHash: sha256:...
```

作者引用 `claimId`，不复制一套新的源码解释。事实审核只重新检查以下情况：

- claim 是新增或修改状态；
- 固定 DSH 提交改变；
- statement、caveat 或证据内容哈希改变；
- 当前部分对 claim 作出了注册表未覆盖的推论。

已经 PASS 且基线、内容哈希和使用语义都未变化的 claim 直接复用。页面间共享事实由构建期引用同一数据源，禁止复制到多份 Markdown 后分别审核。

## 9. 审核结论格式

审核 Agent 只返回结构化结论，不复述全文，不写新的产品总结。建议使用以下 YAML：

```yaml
sectionId: lesson-01
reviewRole: fact | learning-experience
verdict: PASS | REVISE | BLOCK
checkedClaims: [claim.tools-execute.waterfall]
issues:
  - severity: P0 | P1 | P2
    locator: state.result.explanation
    criterion: R0-04
    problem: 在观察结果之前引入了 waterfall。
    requiredChange: 先说明“前一处理者可以决定是否继续”，再在展开层命名。
unresolvedInputs: []
budget:
  inputTokens: 0
  outputTokens: 0
  modelTurns: 1
```

每个审核最多报告 5 个问题；同一根因只报一次。`PASS` 必须没有 P0/P1；`REVISE` 表示范围内可以定点修正；`BLOCK` 只用于事实证据缺失、大纲目标冲突、教学简化改变结论或完成条件不可验证。偏好建议只能标 P2，不能阻塞。

## 10. 冲突裁决

1. 可验证的固定版本事实高于文案流畅和参考站表述。
2. 冻结的用户问题、学习目标和完成条件高于作者或审核人的功能扩展建议。
3. 事实审核决定 claim 是否可发布；体验审核决定当前默认路径是否可理解，但双方不能越权改写对方结论。
4. 两个审核意见冲突时，根负责人查看各自引用的 criterion 和证据，直接作一次裁决；不启动第三个 Agent 投票，也不让两个 Agent 对话。
5. 无法裁决的事实进入 `BLOCK` 并撤出本批发布；无法裁决的风格偏好保持现有版本，不增加回合。
6. 裁决结果写成一条短记录，供后续部分复用，避免相同争议再次消耗审核 Token。

## 11. 何时不应使用子 Agent

以下任务应由当前响应、确定性脚本或根负责人直接完成：

- 打招呼、确认收到、状态查询、简单澄清和单句反馈；
- 错字、标点、纯格式、文件名、已知链接和机械替换；
- lint、类型检查、schema 校验、链接检查、截图尺寸等可确定执行的检查；
- 少于一个完整学习闭环的局部文案，且不引入事实、状态或用户决策；
- 已审核 claim 在相同基线和相同语义下的原样复用；
- 根负责人已经有充分证据可直接裁决的问题；
- 预估固定 Agent 注入成本高于任务正文和预期审核收益；
- 剩余预算不足以让 Agent 完成并给出可用结论；
- 任务会要求读取完整会话、扫描整个仓库或递归委派，但没有明确的信息增益目标。

尤其是“你好”“收到”“继续”这类控制回合，不能触发工具说明、完整项目上下文、子 Agent、检索或后台任务。系统应按意图分级选择上下文：直接对话使用最小对话路径，只有进入文件、代码、浏览器或委派工作时才装载对应工具和项目材料。

## 12. 建议的首批执行方式

1. 根负责人先用一个短文档冻结三课大纲和 claim 列表，不创建写作 Agent。
2. 第 01 课按 A 级运行作者、事实审核、体验审核，验证上下文包和预算是否现实。
3. 根负责人记录每个回合的可见输入、输出、缓存读取、固定注入、时长和结论数量。
4. 若审核发现率低且固定注入占比过高，后两课不增加 Agent，而是缩短审核包或把同类机械检查转为脚本。
5. 第 01 课通过后才复制流程到第 02、03 课；不要同时扩写完整课程目录。
6. 每课完成后保存唯一的审核记录和 claim 状态，不让迟到报告再次触发综合回复。

最终发布门只需要回答四个问题：大纲版本是否冻结、每部分是否有独立的适配风险审核、所有引用 claim 是否有效、所有 Agent 是否已经结束或取消。其余过程信息进入折叠审计记录，不进入学习者主路径。
